# Создание и отображение документов оплаты поставщику из интерфейса 1С

## Общее описание
Механизм обеспечивает:
- Создание документов оплаты поставщикам (OrderPayHead / OrderPaySpec) из интерфейса 1С
- Отображение созданных документов с детализацией по группам номенклатуры
- Просмотр и выбор действующих договоров с поставщиками

Интеграция между 1С и Oracle построена на REST API.
На текущий момент справочник договоров находится в Oracle, поэтому выбор договора выполняется через API-запросы к Oracle.

> **Важно:** После переноса договоров в 1С, логика работы с договорами будет полностью на стороне 1С

## Архитектура
- **1С** - интерфейс пользователя, источник данных о заказах
- **Oracle** - хранение документов оплаты (OrderPayHead, OrderPaySpec)
- **REST API** - интерфейс для передачи данных между 1С и Oracle

## Основные сущности

### 1. OrderPayHead (Заголовок документа оплаты)
Хранит общую информацию о документе оплаты:
- ID заказа
- Дата документа
- Сумма документа
- Договор
- Статус
- Примечание

### 2. OrderPaySpec (Спецификация документа оплаты)
Хранит детали документа оплаты по группам номенклатуры:
- Ссылка на заголовок
- Группа номенклатуры
- Сумма по группе

## Функция расчета вносимых средств  get_order_deposit

### Описание
Функция для расчета распределения суммы вносимых средств по группам номенклатуры заказа.
### Выполняет расчет с учетом:
- Структуры заказа (группы номенклатуры)
- Оплат по заказу (уже созданные документы оплаты)
- Активных договоров поставщика (для каждой группы отдельно)
- Приходных документов

### Синтаксис SQL
 
> Выполнить в Toad и передать в параметр `p_order_rn` (RN заказа поставщику)
```sql
    SELECT * FROM TABLE(get_order_deposit(207212859700, 192249.20));
```

```sql
    FUNCTION get_order_deposit (
             p_order_rn IN NUMBER, 
             p_deposit IN NUMBER DEFAULT 0
    ) RETURN order_deposit_table PIPELINED
```

### Параметры

| Параметр   | Тип    | Обязательный         | Описание               |
|------------|--------|----------------------|------------------------|
| p_order_rn | NUMBER | Да                   | ID заказа из 1С        |
| p_deposit  | NUMBER | Нет (по умолчанию 0) | Сумма вносимых средств |

Таблица с типом order_deposit_table, содержащая следующие поля:

| groupcode          | VARCHAR2(50) | Код номенклатурной группы                          |

## REST API Эндпоинты

### 1. Создание заголовка документа оплаты

Эндпоинт: POST /v1/orderpay/ins_head

Назначение: Создание заголовка документа оплаты (OrderPayHead) в Oracle

Параметры запроса:

| Параметр      | Тип      | Обязательный | Описание                                                          |
|---------------|----------|--------------|-------------------------------------------------------------------|
| orderhead_    | NUMBER   | Да           | ID заказа из 1С                                                   |
| status_       | NUMBER   | Да           | Статус документа (0 - Планируемый, 1 - Оплачен, 2 - Утвержден КД) |
| docdate_      | DATE     | Да           | Дата документа                                                    |
| plandate_     | DATE     | Нет          | Плановая дата оплаты                                              |
| note_         | VARCHAR2 | Нет          | Примечание                                                        |
| orderpay_     | NUMBER   | Да           | Порядок оплаты (0 - Не определен, 1 - ПО, 2 - ПР, 3 - Другое)     |
| num_contract_ | NUMBER   | Нет          | ID договора                                                       |

**Пример запроса:**
```json
{
  "orderhead_": 207364225750,
  "status_": 0,
  "docdate_": "14.07.2026",
  "plandate_": "14.07.2026",
  "note_": "",
  "orderpay_": 1,
  "num_contract_": 142753288730
}
```
**Пример ответа:**
```json
{
  "success": true,
  "message": "Успешно",
  "timestamp": "14-07-2026 17:28:27.426",
  "data": {
    "rn_": 207500311790
  }
}
```

## Реализация в 1С

### Алгоритм работы

1. Получение расчетных данных:
    - Вызов `get_order_deposit` через REST API
    - Получение структуры с группами и расчетами

2. Отображение данных пользователю:
    - Таблица с группами заказа
    - Для каждой группы:
        - Сумма по группе
        - Остаток по группе
        - Найденный договор (если есть)
        - Кнопка выбора договора
        - Сумма вносимых средств на группу

3. **Выбор договора:**
   - Если договор не удалось определить ни для одной группы:
      - Открыть список доступных договоров (вызов `POST /v1/contract/get_contract_agnlist`) и предоставить выбор пользователю
      - После выбора данные из договора использовать для спецификации документа оплаты для каждой группы
   - Если договор найден хотя бы для 1 группы:
      - Брать сведения о типе оплаты из этой группы

4. Валидация суммы:
    - Перед созданием документа проверять: `deposit <= remaining`
    - Если условие не выполнено - выводить уведомление о превышении оплаты
    - По умолчанию подставлять сумму которую необходимо внести (`remaining`)

5. Создание документа:
    - Вызвать `POST /v1/orderpay/ins_head` для создания заголовка
    - Получить `rn` созданного документа
    - Для каждой группы вызвать `POST /v1/orderpay/ins_spec`
    - Обработать возможные ошибки

## Важные нюансы

### 1. Работа с договорами

Если договор по группе не найден автоматически, пользователь должен выбрать его вручную.
В интерфейсе 1С должен отображаться список доступных договоров для поставщика (вызов `POST /v1/contract/get_contract_agnlist`).

Алгоритм выбора:
- Если договор найден хотя бы для одной группы → использовать его тип оплаты для всего документа
- Если договор не найден ни для одной группы → пользователь выбирает договор вручную из списка
- Выбранный договор применяется ко всем группам документа

### 2. Работа с вносимой суммой

Сумма для распределения по группам указывается пользователем самостоятельно.
Обязательное условие: вносимая сумма НЕ должна превышать остаток к оплате по заказу (`remaining`).
В интерфейсе необходимо реализовать валидацию:
- Если `deposit > remaining` — блокировать сохранение
- Показывать предупреждение о превышении
- Автоматически подставлять `remaining` как максимально допустимое значение

При принятии решения о сумме пользователь может ориентироваться на:
- `remaining` — остаток к оплате по заказу
- `prihord_summ` — сумму приходных ордеров по заказу

### 3. Распределение по группам

Сумма распределяется пропорционально долям групп. 
Для групп без договора сумма все равно распределяется (поле deposit_group заполняется). 

### 4. Переплата

Переплата считается как отрицательное число.
Возникает, когда `оплата + вносимая сумма > сумма заказа`.

### 5. Создание документов оплаты

Сначала создается заголовок (OrderPayHead) через `POST /v1/orderpay/ins_head`.
Полученный `rn` используется для создания спецификаций (OrderPaySpec) через `POST /v1/orderpay/ins_spec`.
Для каждой группы создается отдельная спецификация.

## Обработка ошибок

### Ошибки валидации

Deposit > remaining - сумма вносимых средств превышает остаток

Num_contract_group = NULL - нет договора для группы
