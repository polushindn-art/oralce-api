# 🚀 Инструкция по проекту, архитектуре и деплою (Oracle API)

## 📌 Общая информация
Проект представляет собой бэкенд-приложение на **Kotlin** и **Spring Boot** для работы с базой данных **Oracle**. API обслуживает мобильные терминалы сбора данных (ТСД), а также любые другие внешние клиенты и сервисы.

---

## 🏗️ Архитектурные правила и тесты (ArchUnit)
В проекте настроены автоматические архитектурные тесты (`ArchitectureTest.kt`), которые проверяются в обязательном порядке при каждой сборке:

1. **Слоистая архитектура (Layered Architecture):**
    * `Controller` изолирован и не может обходиться без сервисов.
    * `Service` вызывает `Repository`, `Config`, `Exception`.
    * `Repository` доступен только для слоев `Service` и `Config`.
2. **Строгое именование:**
    * Все классы с аннотацией `@RestController` должны заканчиваться на суффикс `Controller`.
    * Все компоненты с аннотацией `@Service` должны заканчиваться на суффикс `Service`.
3. **Изоляция API от базы данных:**
    * Контроллеры не имеют права работать с сущностями БД (`Entity`) напрямую. Вся работа с данными инкапсулирована в сервисах, а наружу отдаются готовые DTO.

## 🛠️ Сборка и деплой через скрипт `push_image_ver.cmd`
Для локальной сборки, проверки тестов, упаковки в Docker и отправки в реестр используется командный файл **`push_image_ver.cmd`**.

### Порядок работы скрипта:
1. **Проверка окружения:** Проверяется наличие `docker` и `mvn`.
2. **Генерация версии:** Версия приложения формируется автоматически на основе количества коммитов в Git (например, `1.25.142`), рассчитывается динамический порт (`8000 + версия`) и имя контейнера (`oracle-prod-...`).
3. **Генерация KDoc и сборка (`mvn dokka:dokka` + `mvn clean package`):**
    * Сначала запускается генерация HTML-документации по коду через **Dokka**, после чего результаты автоматически копируются в статику Spring Boot (`src/main/resources/static/docs`), чтобы «запечься» внутрь приложения.
    * Затем запускается обязательная фаза Maven-сборки и тестирования, включая **ArchUnit**.
    * Если нарушены архитектурные правила или обнаружен прямой вызов `Entity` из контроллера, сборка мгновенно прерывается (`BUILD FAILURE`), защищая production от некорректного кода.
4. **Docker:** Сборка образа, тегирование и `push` в локальный реестр (`oracle-rest-api.ars:5001/oracle-api`).
5. **Очистка:** Удаление старых локальных образов через `docker image prune`.

## 🌐 Инфраструктура и управление (`oracle-rest-api.ars`)
Сервер **`oracle-rest-api.ars`** работает на базе **Ubuntu**:
* **Консоль:** используется для выполнения запуска контейнеров и настройки веб-сервера **Nginx**.
* **Portainer GUI (порт `9000`):** визуальная панель управления Docker. Позволяет наглядно видеть список запущенных контейнеров, управлять ими и при необходимости удалять.
* **Docker Registry (порт `5001`) и Registry UI (порт `7001`):** локальное хранилище образов и веб-интерфейс для контроля их версий.

### 🐳 Описание активных Docker-контейнеров
* **`oracle-dev`** (`8099:8080`) — тестовая среда бэкенда для проверки новых фич и отладки.
* **`oracle-prod-166`** (`8166:8080`) — рабочий production-контейнер приложения актуальной версии, на который настроен проброс трафика через Nginx.
* **`portainer`** (`9000:9000`) — панель визуального управления Docker (Portainer CE).
* **`regime-app`** (порты `50063`, `5063`, `5995`) — вспомогательный микросервис (связанный с системами обмена/маркировки `lm-chz`).
* **`registry-registry-1`** (`5001:5000`) — локальный Docker Registry для хранения образов.
* **`registry-registry-ui-1`** (`7001:80`) — веб-интерфейс (Registry UI) для удобного контроля версий образов.
* **`schemaspy-docs`** (`8070:8080`) — сервис автоматической генерации и хостинга документации структуры базы данных Oracle (**SchemaSpy**).
