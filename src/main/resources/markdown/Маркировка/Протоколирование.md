# Протоколирование изменений кода маркировки в Oracle через триггеры

## 1. Общее описание

В системе реализовано автоматическое протоколирование всех изменений в таблице **MARK** с использованием триггеров Oracle. Это позволяет отслеживать кто, когда и что изменил без необходимости писать код протоколирования в приложении.

---

## 2. Преимущества

- **Автоматическое** — не нужно вызывать протокол в коде приложения
- **Нельзя забыть** — триггер всегда срабатывает при изменении данных
- **BEFORE/AFTER** — есть оба состояния, видно что именно изменилось
- **Реальный пользователь** — берется из JWT токена, а не системный пользователь БД
- **Высокая производительность** — один запрос к БД, без лишних вызовов
- **Атомарность** — в одной транзакции с основным изменением
- **Чистый код** — бизнес-логика не содержит вызовов протоколирования

---

## 3. Архитектура решения

**Spring Boot API:**
1. Пользователь авторизуется и получает JWT токен
2. Запрос проходит через перехватчик `AuditTriggerInterceptor`
3. Перехватчик устанавливает пользователя в контекст Oracle через `PKG_APP_CONTEXT.SET_USER(userName, userIp)`

**Oracle Database:**
1. Выполняется INSERT/UPDATE/DELETE на таблице MARK
2. Срабатывает соответствующий триггер
3. Триггер читает пользователя из контекста через `PKG_APP_CONTEXT.GET_USER_NAME()`
4. Триггер записывает изменения в таблицу PROTOCOL_MARK

---

## 4. Компоненты системы

### 4.1 Таблица PROTOCOL_MARK

Хранит полную историю изменений.

| Поле | Тип | Назначение |
|------|-----|------------|
| RN | NUMBER(17) | Уникальный идентификатор записи протокола |
| TABLE_RN | NUMBER(17) | Идентификатор измененной записи в таблице MARK |
| EVENT_DATE | DATE | Дата и время изменения |
| ACTION | NUMBER(3) | Тип действия |
| BEFORE | VARCHAR2(1024) | Значения полей ДО изменения |
| AFTER | VARCHAR2(1024) | Значения полей ПОСЛЕ изменения |
| USER_NAME | VARCHAR2(100) | Логин пользователя |
| USER_IP | VARCHAR2(50) | IP-адрес пользователя |
| PROGRAMM | VARCHAR2(128) | Приложение (QShop API) |
| NOTE | VARCHAR2(500) | Описание действия |

**Особенности:**
- Партиционирование по полю EVENT_DATE с интервалом 10 дней
- Локальные индексы для быстрого поиска внутри партиций

---

### 4.2 Значения ACTION

| Код | Описание              |
|-----|-----------------------|
| 1   | создание новой записи |
| 2   | статус записи         |
| 3   | дата выбытия          |
| 4   | номенклатура          |

---

### 4.3 Пакет контекста (PKG_APP_CONTEXT)

Управляет сессионными переменными для передачи пользователя из API в триггеры.

| Процедура/Функция | Назначение |
|-------------------|------------|
| SET_USER(user_name, user_ip) | Устанавливает пользователя и IP в контексте сессии |
| GET_USER_NAME() | Возвращает логин пользователя из контекста |
| GET_USER_IP() | Возвращает IP-адрес из контекста |
| GET_USER_RN() | Возвращает RN пользователя из таблицы USERLIST |
| CLEAR() | Очищает контекст после выполнения запроса |

---

### 4.4 Пакет протокола (PKG_PROTOCOL_MARK)

Выполняет вставку записей в таблицу PROTOCOL_MARK.

| Параметр | Назначение |
|----------|------------|
| p_table_rn | RN записи в таблице MARK |
| p_action | Тип действия |
| p_before | Данные ДО изменения |
| p_after | Данные ПОСЛЕ изменения |
| p_note | Примечание |

---

## 5. Триггеры

### 5.1 Триггер на INSERT (TRG_MARK_AUDIT_INSERT)

Срабатывает при создании новой маркировки.

- ACTION = 1 (INSERT)
- BEFORE = NULL
- AFTER = RN созданной записи
- NOTE = "Создание маркировки"

---

### 5.2 Триггер на UPDATE (TRG_MARK_AUDIT_UPDATE)

Срабатывает при обновлении маркировки. Отслеживает изменения полей:

| Поле | Условие | BEFORE | AFTER |
|------|---------|--------|-------|
| STATUS | `:new.status <> :old.status` | Старое значение статуса | Новое значение статуса |
| KM | `:new.km <> :old.km` | Старое значение KM | Новое значение KM |
| JSON | `DBMS_LOB.COMPARE(:new.json, :old.json) <> 0` | Тип изменения | Тип изменения |

**Типы изменений JSON:**
- **added** — JSON был добавлен (был NULL, стал не NULL)
- **changed** — JSON был изменен (был не NULL, стал другим)
- **cleared** — JSON был очищен (был не NULL, стал NULL)

---

### 5.3 Триггер на DELETE (TRG_MARK_AUDIT_DELETE)

Срабатывает при удалении маркировки.

- ACTION = 3 (DELETE)
- BEFORE = Данные удаляемой записи
- AFTER = NULL
- NOTE = "Удаление маркировки"

---

## 6. Схема работы

1. Пользователь отправляет запрос к API с JWT токеном
2. AuditTriggerInterceptor перехватывает запрос до контроллера
3. Перехватчик извлекает пользователя из Spring Security
4. Перехватчик вызывает PKG_APP_CONTEXT.SET_USER(userName, userIp)
5. Контроллер выполняет бизнес-логику
6. Триггер срабатывает после выполнения DML операции
7. Триггер читает PKG_APP_CONTEXT.GET_USER_NAME()
8. Триггер читает PKG_APP_CONTEXT.GET_USER_IP()
9. Триггер записывает изменения в PROTOCOL_MARK
10. AuditTriggerInterceptor вызывает PKG_APP_CONTEXT.CLEAR()
11. API возвращает ответ клиенту

---

## 7. Заключение

Система автоматически протоколирует все изменения в таблице MARK:

| Действие | Что записывается |
|----------|------------------|
| INSERT | Создание новой маркировки |
| UPDATE | Изменение статуса, кода маркировки и JSON |
| DELETE | Удаление маркировки |
| Пользователь | Берется из JWT токена через Interceptor |
| IP-адрес | Берется из HTTP запроса |
| Контекст | Очищается после каждого запроса для безопасности |

Все изменения видны в таблице **PROTOCOL_MARK** и доступны для отчетов и анализа.
